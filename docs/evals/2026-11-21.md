# Eval results, 21 November 2026

40 runs on the three new **gate** cases, graded by hidden tests the agents never see. Every run passed and none was
a false pass. Unlike the [18 November run](2026-11-18.md), these cases reliably need a fix round, so for the first
time the features that act from round 2 on can be measured. Two results:

- **What a fix round sees matters.** Giving the fix round every failing test of a failed check, not only the last
  800 characters of output, cut the average from 3.0 to 2.1 rounds and the cost from $1.54 to $1.06 per run.
- **Session resume makes no measurable difference** on these cases: 9/9 either way, 2.1 vs 2.2 rounds, $1.06 vs
  $0.96 per run. It stays on by default; there is no evidence yet that it pays.

## Setup

- **Cases:** `lib-intervals-perf`, `lib-recurrence-fuzz`, `tickets-export-e2e` (kind `multi-round`). Each has a
  gate suite outside the repo that orch runs after the ordinary checks pass and the agents cannot run
  (`gateChecks`): random inputs against an oracle, a time budget or an end-to-end API flow, plus house rules a CI job
  would enforce and the goal does not state (JSDoc with `@param` and `@returns`, error messages that name the function
  and the bad argument, a BOM and an attachment header on the CSV download). See [evals/README.md](../../evals/README.md).
- **Tier:** `economy`, full loop (`--no-fast`): Sonnet architect, Haiku implementers, Sonnet QA.
- **Repeats:** 3 runs per case and configuration. **Limits:** `--max-rounds 4`, `--max-cost 3`, `--usage-cap 5h=75`.
- **Environment:** Claude Code on Windows, agents without the user's plugins and hooks.
- **Cost** is the CLI's reported `total_cost_usd` (on a subscription it measures usage, not money spent). All runs
  together: $41.

## 1. Making the cases need a fix round (9 runs)

With a gate that only checked what the goal states, all 9 `economy` runs passed in round 1 ($0.54, 1.5 min): the
goal was precise enough that the agents got the behaviour right first time. Adding the unstated house rules to each
gate fixed that: from then on every run needed at least one fix round, as a real project's CI catches what a
ticket never said.

## 2. What the fix round sees (22 runs)

The same 9 runs, after each change to what a failed check passes to the next round:

| code | runs | pass | avg rounds | avg cost | intervals | recurrence | tickets |
|---|---|---|---|---|---|---|---|
| last 800 characters of the output | 4 (usage limit) | 4/4 | 3.0 | $1.54 | 3r $1.37 | 3r $2.06 (1 run) | - |
| every failing test, no stack traces | 9 | 9/9 | 2.3 | $1.32 | 2r $1.12 | 3r $2.03 | 2r $0.81 |
| equal share of 1,500 characters per test | 9 | 9/9 | 2.1 | $1.06 | 2r $0.87 | 2.3r $1.53 | 2r $0.80 |

Before, when a gate failed two house-rule tests, the next round saw only the last one and the other cost an extra
round. Showing every failing test gave each case two rounds (one to build, one to fix). Splitting the output evenly
between the failing tests stopped a long failure from crowding out the others, which mostly lowered the cost.

The first row is only 4 runs (stopped by the usage limit) and the rows ran hours apart, so treat the cost
differences as indicative. The round counts are consistent: every run in the first row took 3 rounds, and no run in
the last row took more than 3.

## 3. Session resume in fix rounds (18 runs)

`economy` lets a fix round's implementer continue its round-1 session (`--resume <id> --fork-session`);
`economy+noresume` starts it cold. Resume happened in all 9 `economy` runs.

| case | resume: pass, rounds, cost | cold: pass, rounds, cost |
|---|---|---|
| lib-intervals-perf | 3/3, 2.0, $0.87 | 3/3, 2.0, $0.84 |
| lib-recurrence-fuzz | 3/3, 2.3, $1.53 | 3/3, 2.3, $1.20 |
| tickets-export-e2e | 3/3, 2.0, $0.80 | 3/3, 2.3, $0.83 |
| **all** | **9/9, 0 false, 2.1, $1.06, 2.4 min** | **9/9, 0 false, 2.2, $0.96, 2.5 min** |

Each configuration had one 3-round run, for different reasons:

- **Resume** (`lib-recurrence-fuzz`): the agent wrote a valid multi-line JSDoc tag with a nested type
  (`@param {{start: string, ...}} rule`), which the gate's JSDoc parser does not recognise. That is a flaw in the
  case, not in orch.
- **Cold** (`lib-recurrence-fuzz`): round 2 fixed the JSDoc but not the error messages, though both failures were in
  its prompt. (`tickets-export-e2e`, cold, also took 3 rounds by design: the repo's own tests failed in round 1, so
  the gate was skipped and only surfaced in round 2.)

The difference in average cost comes almost entirely from the resume run on `lib-recurrence-fuzz` that took 3 rounds
($2.20). Without it, the two configurations cost about the same. A resumed session reads a longer context but does not
need to read the code again, and on fixes this small the two cancel out.

**Decision:** resume stays on. Nothing here argues for or against it. Fixes this mechanical (add a tag, prefix a
message) need no memory of round 1; resume should matter for fixes that need the reasoning behind the first attempt,
which these cases do not test.

## What this means

- **Gate cases work.** 40 of 40 runs passed, none falsely, and all 31 runs with the house rules used a fix round. They
  are the first cases that exercise round-2 features.
- **Next:** fix the `lib-recurrence-fuzz` gate's JSDoc parser (accept nested types and multi-line tags), then
  measure per-task escalation, the diff critic and the review lens on these cases
  (`economy+diffcritic`, `economy+review`), and build a gate case whose fix needs the first round's reasoning to
  test resume again.

## Reproduce

```bash
node evals/run.ts --cases lib-intervals-perf,lib-recurrence-fuzz,tickets-export-e2e \
  --power economy,economy+noresume --repeat 3 --usage-cap 5h=75
```

The run stops at the usage cap and prints a `--resume <stamp>` command to finish the rest after the reset.
