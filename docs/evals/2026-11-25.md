# Eval results, 25 November 2026: repo groups

The first measured runs of repo groups (`orch group run`): 6 runs on three new **group** cases, each a backend and a
frontend repo graded by hidden tests on both. 5 passed; 1 was a false pass. Three results:

- **The contract was never the problem.** The goals leave the API's conventions unstated (lists come in pages of 10
  as `{items, nextCursor}`, errors as `{error: {code, message}}`, money in cents). In all 6 runs the coordinator found
  them in the backend and wrote them into the contract, and no integration check failed, so the fault call and fix
  goals were never needed.
- **The one failure was a member's own QA.** In `group-orders` #1 the coordinator's frontend goal said "listOrders()
  resolves to every order … as an array" and spelled out the cursor loop. The frontend run wrote that loop as
  `listAllOrders()` and exported `listOrders` as the one-page fetcher that returns `{items, nextCursor}`. Its QA and
  the integration check (which compares the live backend with the contract) both passed it.
- **Cost:** $1.62 and 4.2 minutes per group goal on average, for a coordinator, two builds and an integration check.

## Setup

- **Cases:** `group-reviews` (a feature across both repos), `group-price-bugs` (three bugs, two in the web shop and
  one in the API), `group-orders` (stock, a 409 whose code and message the web shop passes on, a paginated list), on
  the `group-shop-api` and `group-shop-web` fixtures. The frontend's hidden tests drive the web client against the
  backend the same run built, so a contract the two sides read differently fails the grade even when each repo's own
  tests pass. See [evals/README.md](../../evals/README.md).
- **Tier:** `economy`, full loop (`--no-fast`) in every member run. The group runs a coordinator, a build per repo
  in parallel, then an integration check: a frontend run against the live backend.
- **Repeats:** 2 runs per case. **Limits:** `--max-rounds 4`, `--max-cost 6` for the whole group, `--usage-cap 5h=85`.
- **Environment:** Claude Code on Windows, agents without the user's plugins and hooks.
- **Cost** is the CLI's reported `total_cost_usd` (on a subscription it measures usage, not money spent): the
  coordinator's calls plus every member run. All runs together: $9.71.

## The false pass, fixed (26 November)

A second run of all six (with a QA rule to check every name the goal states in the code) had the same false pass in
`group-orders`. The cause was the same in both, and it was not the build's QA: the frontend build had written
`placeOrder` and a `listOrders()` that follows every page, as the goal said. The **integration run** then rewrote them.
It only got the integration goal and the contract, which covers the HTTP side and never names the client's functions,
so it "fixed" the client to match the API's shapes (`listOrders` became the one-page fetcher, `placeOrder` became
`createOrder`) and passed its own check.

The integration run now also gets the frontend's goal, with the rule to keep every name, parameter and return value it
states, and to check them by reading the code (only the probe tool reaches the backend). A first wording without that
last part made integration QA try to run the client against the backend and fail rounds as unchecked.

| `group-orders`, economy | runs | hidden pass | false pass | avg rounds | avg cost | avg time |
|---|---|---|---|---|---|---|
| before (25 and 26 Nov) | 4 | 2/4 | 2 | 3.0 | $1.42 | 3.8 min |
| integration goal, first wording | 3 | 3/3 | 0 | 4.3 | $2.07 | 4.5 min |
| integration goal, final | 3 | 3/3 | 0 | 3.0 | $1.28 | 3.4 min |

The second full run, with the QA rule but before this fix: 5/6, the one false pass above, $1.25 per group goal. In one
of the later `group-orders` runs the build's QA caught a `listOrders` that returned the raw page, which is what the QA
rule is for.

## The QA rule on single-repo cases (26 November)

The QA rule above (check every name the goal states in the code) applies to every run, not only groups, so it was
measured on six single-repo cases (`node-duration`, `api-pagination`, `shop-coupons`, `shop-misleading-bug`,
`tickets-workflow`, `tickets-sla`), `economy`, full loop, 2 runs each, with and without the rule, same day.

| economy, 6 cases | runs | hidden pass | false pass | avg rounds | avg cost | avg time |
|---|---|---|---|---|---|---|
| without the QA rule | 12 | 12/12 | 0 | 1.1 | $0.42 | 1.5 min |
| with the QA rule | 12 | 12/12 | 0 | 1.2 | $0.42 | 1.4 min |

No cost and no pass-rate change; the extra round is one `tickets-sla` run that needed two fix rounds and passed. The
rule stays.

## What to do next

- The integration trap never fired, so these cases do not yet measure the fault call or integration fix goals. A case
  whose contract cannot be read off the backend (behaviour only visible when the API is called) would.
- Two runs per case is a small sample; repeat with `--repeat 3` or more before drawing conclusions about pass rates.
