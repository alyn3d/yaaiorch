# Eval results, 18 November 2026

55 runs on 10 cases, graded by hidden tests the agents never see. Every run passed and none was a false pass,
so on today's cases the question is not *whether* YAAIORCH gets there but *what it costs to get there*. The main
result: a single direct attempt is as good as the full architect/build/QA loop on these goals at about half the
cost and time, so it is now the default (`--fast`; `--no-fast` for the full loop).

## Setup

- **Tier:** `economy`. Full loop: Sonnet architect, Haiku implementers, Sonnet QA. Direct attempt (`--fast`): one
  Sonnet agent, judged by the repo's checks; a failure falls back to the full loop.
- **Repeats:** 3 runs per case and configuration. **Limits:** `--max-rounds 4`, `--max-cost 3`.
- **Environment:** Claude Code 2.1.322 on Windows; agents ran without the user's Claude Code plugins and hooks
  (the runner's default since this run), so results do not depend on the machine.
- **Cost** is the CLI's reported `total_cost_usd` (on a subscription it measures usage, not money spent).
- **Hidden pass:** the case's hidden tests and the fixture's own tests pass afterwards. **False pass:** YAAIORCH
  reported success but the hidden tests failed.

## 1. Direct attempt vs full loop (36 runs)

| case | kind | full loop: pass, cost, time | direct attempt: pass, cost, time |
|---|---|---|---|
| node-lru | feature, medium | 3/3, $0.44, 0.7 min | 3/3, $0.14, 0.5 min |
| shop-misleading-bug | bugfix, symptom far from the cause | 3/3, $0.57, 1.1 min (one run took 2 rounds) | 3/3, $0.15, 0.4 min |
| api-pagination | feature, strict validation | 3/3, $0.25, 1.0 min | 3/3, $0.19, 0.6 min |
| node-sortby | feature, multi-key stable sort | 3/3, $0.39, 0.9 min | 3/3, $0.17, 0.5 min |
| py-csv | feature, RFC 4180 by hand | 3/3, $0.42, 1.1 min | 3/3, $0.18, 0.6 min |
| tickets-workflow | long, across layers | 3/3, $0.38, 1.9 min (one run took 2 rounds) | 3/3, $0.30, 1.0 min |
| **all** | | **18/18, 0 false, $0.41, 1.1 min** | **18/18, 0 false, $0.19, 0.6 min** |

The direct attempt never needed the fallback, and it was cheaper and faster on every case. The full loop needed
a second round twice: once because QA asked for a missing assertion in a new test (`shop-misleading-bug`), once
because the repo's own tests failed after round 1 (`tickets-workflow`); both passed in round 2. This matches the earlier
head-to-head in [TODO.md](../../TODO.md) (a single Sonnet call matched the loop up to multi-layer features).

**Decision:** the direct attempt is the default. Plan approval (`--approve-plan`), the plan critic (`--critic`) and
`--dry-run` need round 1's plan, so they keep the full loop unless `--fast` is given too.

## 2. Project brief and notes across goals (12 runs)

Two series cases run three dependent goals on one repo, with (`economy`) and without (`economy+nomem`) the
brief and notes that carry knowledge from one goal to the next.

| case | with brief and notes | without |
|---|---|---|
| tickets-series | 3/3, $1.42, 4.4 min | 3/3, $1.39, 4.5 min |
| api-series | 3/3, $1.02, 3.1 min | 3/3, $1.03, 3.6 min |

Every goal passed in one round either way. On these series the memory neither helps nor costs anything: they are
small enough that each goal can re-read what it needs. This does **not** show that the memory is useless; it
shows these cases cannot tell.

## 3. Fix rounds: session resume and the diff critic (7 of 18 runs, stopped)

`api-patch-contract` was built so that a first attempt breaks a house rule only the repo's checks enforce, which
should force a fix round where session resume (`--no-resume` turns it off) and the diff critic matter. All 7
runs passed in round 1, so neither feature was exercised; the cost differences ($0.28 to $0.41) are run-to-run
noise. The remaining runs (including `lib-retry-lint`, built the same way) were not spent.

## What this means

- **The suite is saturated.** Today's models solve every case in round 1, including the ones built to need several
  rounds. Features that only act from round 2 on (escalation, resume, critics, memory) cannot be measured on them.
- **Next:** harder cases where one context should break down (a small app from a spec, a backlog of dependent
  features, a migration across a larger fixture, a fix-round case that reliably fails first), then measure memory,
  resume and the critics again, and the direct attempt against them.

## Reproduce

```bash
node evals/run.ts --cases node-lru,node-sortby,api-pagination,shop-misleading-bug,py-csv,tickets-workflow \
  --power economy,economy+fast --repeat 3 --parallel 2
node evals/run.ts --cases tickets-series,api-series --power economy,economy+nomem --repeat 3 --parallel 2
node evals/run.ts --cases api-patch-contract,lib-retry-lint --power economy,economy+noresume,economy+diffcritic --repeat 3 --parallel 2
```

On a subscription, add `--usage-cap 5h=60` to leave part of the 5-hour window free; the run stops there and
prints a `--resume` command for the rest.
