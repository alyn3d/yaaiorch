# YAAIORCH architecture

## Overview

YAAIORCH (Yet Another AI Orchestrator) turns a goal into working code by looping specialist agents until QA passes.

    goal ──► architect ──► foundation ──► build (parallel) ──► verify (QA)
                ▲                                                   │
                └──────────── QA failures (next round) ◄────────────┘

Three layers:

| Layer           | Path             | Role                                                                                                                                                                                                                                                               |
| --------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| YAAIORCH CLI    | `orch.ts`        | The loop. Spawns `claude` per agent, validates plans, checks diffs, keeps the queue.                                                                                                                                                                               |
| Claude launcher | `claude-bin.ts`  | Finds the `claude` executable once. On Windows an `.exe` runs directly and an npm `.cmd` shim is unwrapped to node + its script, so no cmd.exe sits between orch and claude (fallback: cmd.exe for a shim it cannot read). PATH only, never the current directory. |
| Agents          | `orch-agents.ts` | Built-in `architect` (read-only planner), `fe`, `be` (implementers), `qa` (verifier). Agents in `~/.claude/agents` or the target repo's `.claude/agents` are discovered automatically and override built-ins of the same name.                                     |
| UI              | `orch-ui/`       | React + TS + SCSS. Runs in a browser (Node server) or as a Tauri v2 desktop app.                                                                                                                                                                                   |

`orch.ts` and `orch-ui/` must sit side by side. The UI looks for `../orch.ts`.

## Desktop packaging

The desktop app ships its own Node.js as a Tauri sidecar (`bundle.externalBin: ["binaries/node"]`). `orch-ui/scripts/fetch-node.mjs` downloads the official build of the pinned `VERSION` for the build's target triple (`--target`, `TAURI_ENV_TARGET_TRIPLE`, or the host's), checks it against the release's `SHASUMS256.txt`, and writes `src-tauri/binaries/node-<triple>[.exe]` (git-ignored; a `.version` stamp skips the download next time). `universal-apple-darwin` is the x64 and arm64 builds fused with `lipo`. Tauri installs it next to the app executable as `node`/`node.exe`; `main.rs` (`node_bin`) runs the server (and so orch) with `YAAIORCH_NODE` if set, else that file, else `node` on PATH. The project's own checks still run with whatever the project uses.

## Orchestrator (`orch.ts`)

### CLI

    orch run "<goal>"     one goal, loop until QA passes or max rounds
    orch add "<goal>"     append to the queue
    orch loop             process the queue (--until-empty to stop when drained)
    orch status           print the queue
    orch agents           list discovered agents and skills
    orch doctor [--json]  first-run checks: node, claude installed and logged in, git, clean repo, leftover checkpoints, checks
    orch account [--json] [--login]  who claude is logged in as (CLAUDE_CONFIG_DIR, else ~/.claude); --login opens a terminal running claude auth login
    orch rollback [BRANCH]  reset to the latest (or given) checkpoint; discarded work kept on orchestrator/discarded-*
    orch prune [--older-than DAYS]  delete orchestrator/* branches older than DAYS (14)
    orch group add|list|remove|run|stop|rollback  one goal across a backend and a frontend repo (see Repo groups)

Options: `--max-rounds N` (5), `--power max|heavy|balanced|economy` (heavy), `--max-cost USD` (per goal, none by default), `--agent-timeout MIN` (30), `--poll S` (15), `--until-empty`, `--dry-run`, `--worktrees` (isolate parallel build tasks; config `worktrees: true`; `--no-worktrees` overrides it). Worktrees require Git. It runs in the target repo (current working directory). Errors print one line; set `ORCH_DEBUG=1` for stack traces.

### Power tiers

Map each role to a model. The architect and QA get the strongest models; implementers get cheaper ones unless a task is flagged `heavy`.

| Tier     | architect | implementer | heavy task | QA     |
| -------- | --------- | ----------- | ---------- | ------ |
| max      | opus      | opus        | opus       | opus   |
| heavy    | opus      | sonnet      | opus       | opus   |
| balanced | sonnet    | sonnet      | opus       | opus   |
| economy  | sonnet    | haiku       | sonnet     | sonnet |

### Round lifecycle (`runGoal`)

1. **Checkpoint** (skipped for `--dry-run`). If the target is a git repo: refuse a dirty tree or a repo with no commits, then create branch `orchestrator/checkpoint-<ts>` and emit `checkpoint`. Without git there is no rollback, no commits and no phantom-completion check.
2. **Architect.** Gets the goal, the agent roster (minus itself), the skill list, the project brief, and from round 2 on what the previous round did (its plan, how each task ended, and the diff stat since the checkpoint) plus its failures, and the plan reply format. Must answer with one JSON `Plan`. **Project brief:** `.orchestrator/brief.md` holds the architect's notes on the repo (stack, layout, conventions, commands). With none, the architect is asked for a `brief` field and orch writes it; later rounds and goals get it in the prompt, and so do every implementer and QA call (with the last 1500 characters of the notes, as `ctx.repoContext`) and the fast path's `dev` agent, so they need not re-read the repo. The architect returns `brief` again only to correct it. The file's first line stamps the commit it describes; when 20 or more files (outside `.orchestrator/`) changed since, or the commit is gone, the first round of the next goal asks the architect to check it, and re-stamps it if nothing needed correcting. `orch learn` (the UI's **Learn repo**) writes or corrects the brief up front in one read-only architect call, with the goal's power, models, budget, usage caps and plugin choice; it emits `learn_start` and `learn_end` (ok, cost), and the server counts that cost toward the daily budget. `--no-brief` (config `"brief": false`) turns this off; delete the file to start over. **Notes:** `.orchestrator/notes.md` collects lessons from earlier goals (QA's optional `notes`, the round-1 failures of a goal that needed several rounds, and what a failed goal left unresolved), newest last, oldest dropped past 8000 characters; past 5000 characters, one read-only call on the implementers' model merges duplicates and drops lessons that no longer apply (`tidyNotes`, event `notes_tidy`, part of the goal's cost; a bad reply keeps the file); the architect (and the fast path's agent) get its last 4000 characters. `--no-notes` / `"notes": false`.
   2b. **Plan critic** (`--critic`, config `"critic": true`, off by default). The built-in read-only `critic` agent (never given tasks) reviews the plan with only the goal, the brief and the plan, never the architect's reasoning, and answers `{approved, issues[]}` on QA's model. A rejection goes back to the architect once with the issues; the revised plan is not reviewed again. A critic error that is not a budget or usage limit just approves. Emits `critic`; its cost is part of the plan's. A reply that is not valid JSON or fails validation is sent back once with the reason.
   2b'. **Plan approval** (`--approve-plan`, config `"approvePlan": true`; not on the fast path's direct round or a dry run). After the critic, orch writes `.orchestrator/plan-pending.json` ({goal, round, plan}), emits `approval_wait` (round, summary, tasks, error?) and polls for `.orchestrator/plan-decision.json`, without a time limit. `orch approve` writes that answer: approve, approve with an edited plan (`--plan-stdin`, validated against the agents before it is written, and again by the run, which waits again with `error` if it is still invalid), or `--reject "why"`, which goes to the architect as a note; the new plan waits again. Each answer emits `approval` (round, action, edited). The server calls `orch approve` and pass an edited plan on stdin.
   2b'''. **Agent M: approved shell commands** (`--commands`, config `"commands": "ask"`, off by default). Headless implementers run with `acceptEdits`, which refuses shell commands that need permission. With `--commands`, each implementer call (never the architect, QA, critics or reviewers) gets `--mcp-config` with a per-call file naming `orch permit` and `--permission-prompt-tool mcp__agentm__approve`, so the CLI asks that MCP server before such a tool call. `orch permit` denies every non-shell tool as before; for Bash/PowerShell it allows a command already in config `allow`, else writes `.orchestrator/commands/<id>.json` (tied to the run lock) and waits for `<id>.decision.json`, which only `orch decide ID allow|deny|always|prefix` writes (once, through a claim file). It answers the CLI with `{behavior: "allow", updatedInput}` or `{behavior: "deny", message}`, so the agent sees why. `always` also adds the exact `Bash(<command>)` rule to config `allow`; `prefix` adds `Bash(<first two words>:*)` (`prefixRule`: a single command with more after two plain words, never a shell, interpreter, destructive command or run-any-package subcommand), and `allowedBy` matches it for a single command only, never a chained one. No answer within `--command-timeout` (default 10 min), or the run ending, denies it. The run process polls the directory and emits `command_wait` / `command_decided`; while one of a call's commands waits, `--agent-timeout` does not fire. The UI's Agent M page lists waiting commands across repos and answers through the server (`/api/decide-command`). The same page has a chat: `orch chat` asks Haiku (read-only tools, no MCP servers, `--add-dir` per open repo, `--resume` for follow-ups from a fixed directory `~/.yaaiorch/agent-m`) with a redacted status of the machine (doctor, plugins, `claude mcp list`, cached 10 minutes) and each repo (queue, last run, recent runs with failures, brief); the backends add its cost to the daily spend.

2b''. **Agent questions** (`--ask`, config `"ask": true`, off by default). Goal agent prompts allow a structured question instead of the usual reply; the Claude turn finishes and must include a session ID. Orch emits `question_wait`, waits without a timeout, then continues the forked session with the answer and original reply contract. Each pending question has a random ID and a separate file tied to the current run lock, so parallel questions do not collide and stale ones cannot be answered. `orch answer ID` reads stdin, claims that question once, and atomically writes its answer; the server calls it. Recognized secrets are redacted from question events; answers are not emitted but are briefly stored on disk and passed to the agent. Files are removed after answering or normal exit, and stale question files are removed when the next run takes the lock. A continuation failure is reported rather than silently starting a new session. History shows questions without live controls.
2f. **Big briefs** (`orch split`; also used by `orch new`). `splitBrief` makes one read-only architect call with the brief (up to 100,000 characters) and, for an existing repo, the instruction to read it first; the reply is at most 30 goals in build order, each starting with the part of the brief it covers, plus checks for a new project. It emits `split_proposal` (goals, checks?, cost). `--propose` stops there (the UI shows the list to edit); `orch split --accept` takes `{brief, goals}` on stdin. Accepting writes `.orchestrator/spec.md` and queues the goals with `fromSpec: true`. `makePlan` puts the first 15,000 characters of spec.md in every architect prompt. **Coverage:** when `loop` finds no pending goal, and goals from the brief have finished since the last check (`.orchestrator/spec-state.json`), one read-only call compares the brief with the code and the goals run, and queues at most 5 missing goals (event `coverage`: pass, missing, cost); at most two passes per brief, `--no-coverage` / `"coverage": false`. The server passes a brief to `orch split --propose` in a temporary file that orch deletes (`--brief-file-temp`) and count both events' cost. `split_proposal` has `queued: true` when the goals were queued at once (`orch new`, `orch split` without `--propose`), so a UI does not offer them again. The UI's **+ New project** has the server create `<parent>/<name>` (the name is a plain folder name), open it as a repo tab and run `orch new .` there (spec in a temporary file); a folder holding only `.orchestrator/` counts as empty.
2g. **Dependencies, retries, blocked goals.** The splitter answers `{goal, after}` per goal, `after` being 1-based positions of the earlier goals it needs (a plain string or a missing `after` means all earlier ones; later positions are dropped). `acceptSplit` stores them as queue ids in `after`, and the brief's id in `brief`. `loop` takes the first pending goal whose `after` goals are all `done` (`nextRunnable`); before that, `blockDependents` marks pending goals that need a `failed` or `blocked` goal as `blocked` (event `blocked`, with a note naming the goal), down the chain. A goal that fails (not for a budget) is set back to pending once per `--retries` (config `retries`, default 1, 0 to 3) with `power` one tier higher and alias models stepped up (event `retry`); only then is it `failed`. After each goal the loop adds its cost and seconds to the queue item (all attempts) and emits `queue_changed`; the the server sends the queue again on that and on `queue_item`, `blocked` and `coverage`, and the UI's `progress.ts` shows the latest brief's progress from it. `orch retry ID` (UI **Retry**) puts a failed or blocked goal and the goals it blocked back to pending with a fresh retry budget. The coverage check waits while any goal of the brief is blocked.
2i. **Resuming an interrupted goal.** When the usage limit cuts a goal short, its work is parked (`orchestrator/interrupted-*`, or it stays on its own `--branch` goal branch, or is parked from a brief's shared branch) and the branch is remembered: `resumeFrom` on the queue item in `loop`, a variable across the retries of `orch run --on-limit wait`. The next attempt brings those commits back after its checkpoint (`applyParked`: a fast-forward, or a cherry-pick if the branch moved; if that fails the goal starts fresh and the branch is kept), deletes the parked branch, emits `resumed`, and tells the architect in its first round that the work is there, so it plans only what remains (just the verify task if it looks complete).
2h. **Shared brief branch** (`--branch` with goals from a brief). `prepareGit` runs the branch switch after the dirty check and before the checkpoint, so the checkpoint is on the goal's branch. Goals of one brief use `orch/brief-<id>` (created by the first, switched to by the rest), so each builds on the ones before. A failed goal there is parked with `moveWorkAside` (`orchestrator/failed-*`) and the shared branch reset to its checkpoint. With `--pr` the first passed goal opens one pull request for the brief (title: the brief's first line, body: the brief), stored in `spec-state.json`; later passed goals push to it (`pr` event with `updated`).
2j. **Intake** (`orch intake --github LABEL --backlog FILE`, `loop --intake github:LABEL,backlog:FILE`, config `intake`). GitHub: `gh issue list --label L --state open --json number,title,body` (gh found like claude, `GH_BIN`), oldest first; the goal is the title and the body (first 4,000 characters), the item keeps `issue`. A backlog file: each unchecked `- [ ]` item with its indented lines, keyed by a hash of its text (`backlog`); the file is never changed. Anything already in the queue (any status) is skipped. Event `intake` (source, ids). A loop with `--intake` runs it whenever no goal is runnable, before the coverage check; a failing intake is reported and tried again later. A goal from an issue carries `issue` into `last-run.json`, and its pull request body says `Closes #N`. Issue text becomes agent instructions: the label is the gate. **Priority:** labels `p1`-`p9` (also `orch:p2`, `priority:p1`) or `priority: urgent|high|medium|low` (`priorityOf`), or `(p1)` at the start of a backlog item, set `priority` (default 3); `nextRunnable` takes the lowest among the runnable goals, then queue order. **Comments** (`commentIssue`, `gh issue comment N --body-file -`, never fatal; `--no-issue-comments` / `issueComments: false`): when a goal from an issue starts (first attempt), ends done (with the PR or branch) or failed for good (the last failures and how to retry), and when it is blocked. Queue goal numbers are written as "queue goal N", never "#N", which GitHub would link to an issue.
2k. **CI of the pull request** (`--pr`; `--ci-fixes N`, default 2, 0 to only report; `--no-ci-watch`, config `ciFixes`, `ciWatch`). After a passed goal opened or updated its pull request, `watchPullRequest` polls `gh pr checks <pr> --json name,bucket,link` (`ORCH_CI_POLL_MS`, 30 s) until nothing is pending (`ORCH_CI_TIMEOUT_MS`, 30 min; no checks after `ORCH_CI_NONE_MS`: `none`) and emits `ci` (state, attempt, failed names). While checks fail and fixes are left: the failing jobs' logs (`gh run view <run> --job <job> --log-failed`, last 4,000 characters each) go into a fix goal ("do not weaken, skip or delete checks"; protected paths still apply), run with `runGoalInner` on the PR branch with its own checkpoint, `goal_start` / `goal_end` and commit title `fix CI of <goal>`, at most 3 rounds and no approval gate; a passed fix is pushed and CI is awaited again, a failed one is parked and the branch left as the PR had it. `last-run.json` records `ci`, and the issue comment says whether the checks pass.
2e. **New project** (`orch new DIR "<spec>"`, `--spec-file`, `--setup CMD`; not part of a run). Refuses a folder that is not empty. Creates it, `git init` on `main`, commits `SPEC.md` and a `.gitignore` (`.orchestrator/`, dependency and build folders), seeds the brief with the spec, then one read-only architect call returns `{goals[], checks{}}`: at most 12 goals (the first sets the project up) are queued, and at most 4 valid checks plus `setup` go into `.orchestrator/config.json`. It builds nothing; the user reviews and runs `orch loop`.
2c. **Share** (`orch share`, the UI's **Share to CLAUDE.md**; not part of a run). One read-only architect call turns the brief, the notes and the current `CLAUDE.md` into the body of a section between `<!-- yaaiorch:learned:start -->` and `<!-- yaaiorch:learned:end -->` (replacing an earlier one; everything else in the file is kept). orch commits it with git plumbing (a temporary index, `commit-tree`) on a new `orchestrator/claude-md-<ms>` branch off HEAD, so neither the working tree nor the index changes; the user reviews and merges it. `--dry-run` prints the section. Takes the run lock; the backends count its cost.
2d. **Branch per goal** (`--branch`, config `"branch": true`; `--pr` implies it). After the checkpoint, orch switches to a new branch `orch/<queue id or time stamp>-<slug of the goal>` (event `goal_branch`, with the base branch; a detached HEAD is refused). Every round commits there. At the end, whatever the outcome, orch commits what is left, switches back to the base branch (which never moved) and deletes the checkpoint; a goal branch without commits is deleted, any other stays. If the work cannot be committed, orch stays on the goal branch and keeps the checkpoint. In a loop each goal branches from the base, not from the goal before. With `--pr` (config `"pr": true`), a passed goal's branch is pushed to `origin` (`GIT_TERMINAL_PROMPT=0`, so a credential prompt cannot hang a run) and `gh pr create --base <base> --head <branch> --title <goal> --body-file -` opens the pull request, its body (the goal, each round's plan, checks and cost) on stdin. `gh` is found like `claude` (`GH_BIN` overrides; no shell on Windows). The push works with any host. `gh` runs only when origin is on GitHub (`forgeOf` on `remoteWeb` of `remote.origin.url` as configured, not `get-url`, which applies `insteadOf`); for another host, or GitHub without `gh`, the `pr` event carries `link`: the create link the host printed on push (`pushLink`), else one built for GitHub, GitLab, Bitbucket or Gitea/Forgejo (`newPullRequestUrl`). CI watching and issue comments need an opened pull request, so they stay GitHub-only. A missing remote, a missing or failing `gh` is reported in the `pr` event (`url`, `link` or `error`) and never fails the goal. `last-run.json` records `branch`, `base` and `pr`. 3. **Validate.** Rejects a malformed plan, unknown agents, invalid phases, foundation/build tasks without files, a file owned by two tasks (paths normalized: `./`, `\`, case on Windows), and plans with no `verify` task. Plans are untrusted input: every file path must be relative to the repo root (no absolute, drive or UNC path, no `..`), must not be in `.git/` or `.orchestrator/`, and must not resolve outside the repo through a symlink or junction (checked on the deepest existing part); at most 25 tasks and 60 files per task. The error names the task and the file. 4. **Foundation** tasks run one at a time (shared types, tokens, API client). If one errors, the rest of the round is skipped (`SKIPPED`). 5. **Build** tasks run in parallel. File ownership is what makes this safe. With `--worktrees` (off by default), each task gets a detached Git worktree seeded from the same snapshot after foundation tasks. Existing top-level ignored dependency folders (`node_modules`, `.venv`, `venv`, `.tox`) are linked from the main worktree. Once all tasks finish, orch applies their diffs to the main worktree in plan order; a diff that cannot be applied leaves that task's worktree intact and fails the task with its path for recovery. Task-session resume between rounds is disabled in this mode. A task that errors does not stop its siblings; its error becomes a round failure. **Ownership check:** afterwards, files changed outside every task's list (git status against the files changed before the round) are logged and sent as `unowned`; QA gets the list with the diff, and with `--strict-files` (config `strictFiles`) they fail the round. Plans without file lists (the fast path) are exempt. 6. **Commit.** First the safety checks: files changed under a protected path (`protect`, default `.github/workflows/`; `protectRe` globs: `dir/`, `*`, `**`) are reverted to HEAD (new ones removed), emit `protected` and fail the round; `validate` already rejects a plan that lists one. Then `scanSecrets` looks at the lines added since HEAD, every new file and any `.env` file for known key formats and private keys (`SECRETS`); a finding emits `secrets` (file and kind, never the value), skips the commit and fails the round, and `commitAll` refuses such a commit anywhere except on orch's own side branches. Then all changes except `.orchestrator/` are committed on the current branch (`orch: <goal> (round N)`); with `--branch` that is the goal's own branch. If the commit fails (for example a hook), the round continues uncommitted. 7. **Checks.** First, if the config has `setup` (for example `npm install`) and a watched manifest or lock file (`setupWhen`, default package.json, lock files, requirements.txt, pyproject.toml, go.mod, Cargo.toml, ...) changed since it last succeeded (`.orchestrator/setup-state.json`), orch runs it (a check named `setup`; if it fails, no other check runs and the round fails). Untracked directories it creates that git does not ignore go into `.git/info/exclude`. The checks are read again here and at each round start, so a package.json the agents just wrote counts. Implementers are told to add dependencies to the manifest, never to install them. The orchestrator runs the repo's check commands itself (10 min timeout each) and emits `checks`. Commands come from `.orchestrator/config.json` `checks`, else from the package.json scripts `typecheck`, `lint`, `test`, `build` (npm's placeholder test is skipped). **Gate checks** (config `gateChecks`, `loadGateChecks`, read once at run start, so an agent editing the config cannot change them) run after the ordinary checks, only when all of them passed; their results carry `gate: true`, skipped ones are listed in `gateSkipped`. They never reach the agents' allow-list (each gate command is also a deny rule, which beats any allow), a round that already failed skips them, a gate failure line names the gate without its command (failures reach notes.md), and agents get only their names (`gateHint`: the architect via `GATE_HINT`, the fast path's `dev`, `orch learn`); `gateOverlap` warns at run start (and `orch doctor`) when an ordinary check's prefix rule would also allow a gate command. A gate failure is a check failure, so it drives the fix round like any other.
7b. **Browser checks** (`orch-browser.ts`; only with config `serve` and without `--no-visual` / `"visual": false`). At goal start `visualSetup` checks `serve` (the url must be on this machine: localhost, 127.0.0.1, [::1] or `*.localhost`), finds a browser (`YAAIORCH_BROWSER`, Chrome for Testing from `orch browser install`, else an installed Chrome, Edge, Chromium or Brave), clears `.orchestrator/visual/` and adds a "Browser checks" section to the architect's prompt. A verify task may then carry `visual`: at most 5 pages per plan, each `{path, selector?, actions?: [{click} | {wait}], viewports? (default 1280 and 375), themes? (default light)}`, checked by `validateTargets` (a path in the app, never a host). On a round where no task errored and every check passed, `DevServer` makes sure `url` answers (starting `command` through the shell, like the checks, with `BROWSER=none`; restarted after `setup` ran; kept for the rest of the process and killed with its tree on exit). The UI can also discover common web scripts in the root or an immediate child, show the script and lifecycle commands for approval, and save an automatic `serve` configuration. Before starting it, orch verifies the approved scripts are unchanged and discovers a responding localhost URL from the server's output. Manual `serve` configurations are never overwritten by detection. `captureVisual` starts the browser headless on the repo's profile (`~/.yaaiorch/browser-profiles/<hash of the repo path>`, so `orch browser login` sessions carry over), talks CDP over Node's built-in WebSocket (Node 22+), and per page, theme and width: emulates the width (mobile under 768px) and `prefers-color-scheme`, navigates, waits for the selector, runs the actions (clicks and waits only), screenshots the selector's box (else the page, capped at 8000px) into `.orchestrator/visual/round-N/`, and measures overflow against the width asked for, blank pages and dev-server error overlays. **Problems** fail the round (`browser check: ...`): navigation errors, HTTP 4xx/5xx for the page, a blank page or build error overlay, a selector or click target not found in 10s, the page leaving the app's origin, a browser that cannot start, a dev server that does not answer in `timeout` seconds (with its output). **Observations** go to QA only, since they may predate the change: uncaught page errors, console errors, failed requests (not favicon), horizontal overflow, cumulative layout shift over 0.1. Emits `visual`. Each verify task's prompt gets `visualReport`: its own pages' screenshot paths (QA opens them with Read; the narrowest one per page and theme is marked required, since a real QA run otherwise sampled two and skipped a page's dark theme), the problems and the observations. 8. **Diff reviews** (off by default), started next to the verify tasks when no task errored and every check passed (a failed check wins, so nothing is spent on reviews then): `--diff-critic` (config `diffCritic`) has the `critic` read the change against the goal (lens `goal`); `--review` (config `"review": true`) has the built-in read-only `reviewer` read it for bugs and security (lens `bugs`), or your own agents with `--reviewers A,B` (config `"review": ["A", "B"]`; unknown names are refused). Each gets the goal, the brief and notes, the diff stat and the patch since the checkpoint (first 30,000 characters), answers `{approved, issues[]}` on QA's model, and emits `review`. A rejection's issues become round failures (`<agent> (review): ...`); an error that is not a budget or usage limit approves. Reviewers and the critic are never given tasks. 9. **Verify** tasks run sequentially, never edit. Each returns `{passed, failures[]}`. They receive the implementer reports, the diff stat against the checkpoint, any uncommitted new files, and the check results with output tails. A verify call that errors counts as a failure. 10. Write `.orchestrator/last-run.json`. The round passes only if no task errored, every check exited 0, every verdict passed and every diff review approved. A failed check is a failure whatever QA says. Otherwise feed the failures to the next architect round. 11. **Stuck detection.** A failed round that changed no files, or ended with the same failures as the round before (compared ignoring case, spacing and numbers), counts as stuck. The first time the architect is told not to repeat its plan, and something moves one power tier up (economy → balanced → heavy → max): if some implementer tasks failed outright (FAILED, PARTIAL, PHANTOM, ERROR, UNKNOWN) while others completed, only those tasks' agents move up (their tier and alias overrides; `stuck` carries `agents`, `round_start` then `agentPower`); otherwise, when every task claims success and the plan or verification is the problem, the whole round moves up (`stuck` with action `escalate`, or `retry` at max). Two stuck rounds in a row stop the goal (`stuck`, action `stop`). 11. **Finish** (git only). On pass, delete the checkpoint. On failure in `loop`, move the goal's commits to `orchestrator/failed-<ts>` and reset the branch to the checkpoint, so the next goal starts clean. On failure in `run`, leave the commits; `orch rollback` (or the UI button) undoes them.

### Fast path (default; `--no-fast` or config `"fast": false` to turn off)

On by default since the [November 2026 evals](evals/2026-11-18.md) (every case passed, at about half the cost and time of the full loop); `--approve-plan`, `--critic` and `--dry-run` need round 1's plan, so they turn the default off unless `--fast` is given too. Round 1 skips the architect: one generalist `dev` agent does the whole goal on the tier's heavy model, with no file list (so no phantom check). The repo's checks judge it; when no checks are configured a QA task is added. `round_start` carries `mode: "direct"`. If the round fails, later rounds run the normal loop with its failures. The evals compare it with `--power economy+fast` against the full loop (a plain tier passes `--no-fast`) and `--single`.

### Limits

- **Agent timeout** (`--agent-timeout`, 30 min): a call that runs longer is killed with its whole process tree (`taskkill /T` on Windows) and becomes a task error.
- **Session resume** (`--no-resume` or config `"resume": false` to turn off): every CLI reply carries a `session_id`.
  In a fix round, an implementer task continues the session of the same agent's task from the round before that
  shares a file with it (most shared files wins; with no file lists, only one task per agent then and now), with
  `--resume <id> --fork-session`, so parallel tasks and retries never share a session. Its prompt is the new task
  alone: the session already has the brief, the files it read and what it did. After a stuck round every task
  starts cold, so a failed approach is not carried on; QA and the architect never resume. If resuming fails (the
  session is gone), the task starts cold once. A phantom completion's retry continues its own session and is told
  which files did not change. `task_start` has `resumed: <round>` (a badge in the run panel).
- **Transient errors**: a call whose CLI error text shows an API overload, a 5xx or 429 API error, or a dropped
  connection (`TRANSIENT_RE`) is retried once after 15 s (`ORCH_RETRY_DELAY_MS`). Never the usage limit, the
  budget or an agent timeout, and never a task's own failure.
- **Loop budget** (`--max-cost-total`, config `maxCostTotal`, `loop` only): the goals of one loop run share it;
  each goal's `--max-cost` is capped to what is left, and the loop stops before its next goal (`loop_stop`,
  reason `budget`) once it is used up. When the loop budget (not the goal's own `--max-cost`) runs out during a
  goal, that goal stays `pending` with a note, is not retried and blocks nothing, and the loop stops at once; a
  later loop with more budget carries on. A goal that exceeds its own `--max-cost` fails as before. The server passes what is left of the UI's daily budget to a
  `loop` (and to `orch new --start`) as `--max-cost-total`, so the daily budget stops a queue the same way; a single
  goal or call gets it as `--max-cost`.
- **Budget** (`--max-cost`): every call's `total_cost_usd` is added to the goal's total, also for failed calls. Before it starts, each call reserves its share of the unreserved budget and gets it as `--max-budget-usd`: alone, all of it; in the parallel build batch, an equal share per task still to start (with $0.20 left, two build agents get $0.10 each). When the call ends its reservation is released and its real cost counted, also on failure, timeout or a spawn error. A call that would get less than $0.01 waits while others hold reservations, and otherwise stops the goal. When the CLI reports `error_max_budget_usd`, or the total reaches the cap, the goal stops with `Stopped: budget of $X used up`. The CLI checks its limit after each turn, so a call can overshoot its share by up to one turn.

- **Usage limit**: the Claude subscription limit comes back as an error result with subtype `success` and text like `You've hit your 5-hour limit · resets 1:30am (Europe/London)`. `run()` turns it into a `UsageLimit` error (reset time parsed in the named IANA zone) that ends the goal instead of becoming a task failure, so it never triggers stuck detection. It emits `usage_limit`, then `goal_end` with `usageLimit: true, resetAt`. What happens next is the **"when the usage limit is hit"** setting (`--on-limit`, config `onLimit`):
  - `wait` (default): the goal's work moves to `orchestrator/interrupted-*` and the branch is reset to the checkpoint; orch waits until a minute after the reset (30 min if the reply has no time; `ORCH_LIMIT_WAIT_MS` overrides it for tests), emits `waiting`, and retries the goal. In `loop` the item goes back to `pending` with a `note` meanwhile.
  - `stop`: `orch run` exits with **code 3** (commits kept, `orch rollback` available). In `loop` the work is set aside, the item stays `pending` with a "stopped" `note`, and orch exits 3.
- **Keep awake** (`orch-awake.ts`; `--keep-awake`, config `keepAwake`, `--no-keep-awake` wins): `run`, `loop`, `new --start` and `group run` (never a group's member runs: `ORCH_GROUP_LOCK`) start a helper that blocks idle sleep while orch lives, so a `wait` above ends on a machine that is still on (the wait compares wall-clock time, so it also resumes after a sleep). Windows: the system `powershell.exe` by full path with an `-EncodedCommand` script that calls `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)` every 30 s while orch's PID exists; macOS: `/usr/bin/caffeinate -i -w <pid>`; Linux: `systemd-inhibit --what=idle` around a `kill -0 <pid>` loop. orch also kills it on exit. Where none applies it says so and runs as before. The display may sleep; a lid close or an explicit Sleep is not blocked. The server holds a global **Keep computer awake** switch (on by default, persisted with the repos) and adds `--keep-awake` to those commands (`withAwake`).

### Models

Each power tier maps the roles `architect`, `impl`, `heavy`, `qa` and `dev` (the fast path's agent, the tier's heavy model by default) to models. `--model architect=opus,impl=haiku,be=claude-…` and `.orchestrator/config.json` `"models": { "architect": …, "agents": { "be": … } }` override them: a per-agent override beats a per-role override, and the CLI beats the config. An override for an agent that does not exist fails the goal. When a stuck round moves up a tier, alias overrides (`haiku` → `sonnet` → `opus`) move up with it; full model IDs stay as set. Each `round_start` carries the effective `models`.

### Rollback and pruning

`orch rollback` picks the newest `orchestrator/checkpoint-*` (or the given branch), refuses if it is not an ancestor of the current branch, commits whatever is left (including uncommitted edits from a stopped run), keeps that on `orchestrator/discarded-<ts>`, resets to the checkpoint, deletes the checkpoint and clears it from `last-run.json`. Nothing is lost. `orch prune` deletes `orchestrator/*` branches whose timestamp is older than `--older-than` days, never the current branch.

### Plan shape

    Plan = { summary, tasks: Task[] }
    Task = { agent, phase: "foundation"|"build"|"verify", task, files?: string[],
             heavy?: boolean, figma?: string, skills?: string[] }

### Trust model: diff over report

Agent reports are not trusted. `execute()` hashes each owned file (`git hash-object`) before and after. If an agent says `Status: COMPLETE` but no owned file changed, that is a phantom completion: it is re-dispatched once, then recorded as `PHANTOM`.

### Running agents (`run()`)

Each agent is a one-shot headless call:

    claude -p [--agents .orchestrator/builtin-agents.json] --settings <settings> --agent <name> --model <m>
              --output-format stream-json --verbose --permission-mode <mode> [--max-budget-usd <share>]

`--agents` is added for built-in agents. Implementers run with `acceptEdits` and `agent-settings.json`. The architect and verifiers are read-only: permission mode `default` with `readonly-settings.json`, which adds a deny on Edit/Write/MultiEdit/NotebookEdit. Denying the edit tools alone is not enough: under `acceptEdits` an agent wrote a file with a shell redirect instead (confirmed with the real CLI), while `default` refuses that and still runs allow-listed commands. In `-p` mode with `acceptEdits`, a shell command that needs permission is refused unless allowed (confirmed in a real run; commands Claude Code treats as read-only, such as `echo` or `ls`, run without asking, and with `--commands` the rest go to Agent M), so `agent-settings.json` allows the check commands (`Bash(...)` and `PowerShell(...)`), `npm test` and read-only git, plus anything in `.orchestrator/config.json` `allow`. Compound commands (`cd x && npm test; echo $?`) still do not match those rules, which is why the orchestrator runs the checks itself rather than relying on QA. The prompt goes through stdin (no quoting problems on Windows). The JSON reply is parsed even on a non-zero exit, so the cost and the reason (`subtype`) are kept. A reply with `is_error`, a non-zero exit or no string `result` is an error. `extractJson` prefers a fenced `json` block, then the outermost `{...}`. The process is spawned without a shell (see `claude-bin.ts`), with `windowsHide`.

### Reply contracts

`orch.ts` appends the required reply format to every prompt, so discovered agents follow it too: the architect returns a JSON `Plan`, implementers end with `Status: COMPLETE|PARTIAL|FAILED`, verifiers return JSON `{passed, failures[]}`.

### Repo groups (`orch-group.ts`, `orch-group-run.ts`)

`orch group run NAME "<goal>"` builds one goal across a group's backend and frontend repo (version 1: exactly one of each). The group process runs in neither repo: it holds the group lock (`~/.yaaiorch/groups/<name>/run.lock`) and both repos' run locks, and passes the lock ids to its children in `ORCH_GROUP_LOCK`, so a child does not take (or refuse) the lock again. It must not import `orch.ts`, so the lock and atomic-write helpers come in as `GroupDeps`; every repo-level git step runs as a hidden `orch group-member checkpoint|park|drop|head|has|verify|reset|branch|unbranch|publish|pr-body ...` child in that repo (`branch`, `unbranch`, `publish` and `pr-body` only with `--branch` / `--pr`: a group branch per repo after the checkpoints, back to the base after a park or a pass, then a push and a pull request per repo, the backend's rewritten to link the frontend's), and the coordinator as `orch group-member coordinate plan|fault` (JSON on stdin, one JSON line on stdout) in the backend repo, so it reuses `runOnce`, budget, models and swaps.

1. **Checkpoint** both repos (`orchestrator/checkpoint-*`).
2. **Coordinator** (read-only, the other repo readable) replies `{contract, goals: {backend?, frontend?}}`; `group_plan`. With `--approve-plan`, `group-dir/plan-pending.json` waits for `plan-decision.json`, which only `orch approve --group NAME [--reject WHY | --plan-stdin]` writes (an edited plan is `{contract, goals}`; a rejection re-asks the coordinator). The contract goes to `.orchestrator/contract.md` in both repos (never committed) and, with the other repo's path, to a `--group-context` file per repo.
3. **Build**: one `orch run` child per repo with a goal, in parallel, with `--group-context`, `--read-dir <other repo>`, `--strict-files`, `--no-commands` (no Agent M) and the group's `--on-limit`; the goal comes last, after `--`, so one that starts with `-` is not read as an option. The other repo is readable but writes to it are denied in the child's settings (a `--read-dir`, or a member path, with `[ ] * ? { } !` or a UNC path is refused: its rule would not hold; spaces and parentheses were checked with the real CLI). A script can still write there: after every build, integration and fix step the group asks both repos for uncommitted changes (`group-member head` returns `dirty`) and fails, naming the files, on any; that also catches a member whose final commit failed. In a member run the repo's own `branch`, `pr`, `approvePlan`, `worktrees` and `ask` settings are ignored. The frontend's group `env` (`{backend}` replaced) reaches the frontend's children in every step, build included; an entry still containing `{backend}` (no serve) is left out. The first failing child stops the other.
4. **Integration**, with a backend `serve` (the group's, else the backend repo's config; none: skipped, `group_step` with `skipped`): a `DevServer` starts the backend in its repo with `serve.command`, then a frontend child with `--no-fast` verifies the frontend against it. Headless agents have no shell, so the child runs with `--probe <backend base URL>`: each agent call gets a second `--mcp-config` file for `orch probe` (`probeServer`), an MCP server whose one tool, `request`, sends an HTTP request to that backend's origin only (`probeTarget`) and returns the status, content type and body; `--allowedTools mcp__probe__request` lets read-only roles use it. The goal (`integrationGoal`) asks for every case the frontend relies on to be checked live through it, and counts a case that could not be checked as a failure. The fault call blames a side only for behaviour the report shows. Something already answering at the URL that the group did not start fails the step (`group_step` with `failed`, no fault call): it would not be the code just built. Without a `command` the person runs the backend: an answering one is used (a warning, `group_step` with `external`), and a backend fix fails the group ("backend changed; restart your backend and rerun"). On failure the coordinator's fault call (`group_fault`) names the side(s) at fault and gives each a fix goal (a goal for a side not at fault is dropped); it may revise the contract (rewritten everywhere, `group_plan` with `revised`). The fix children run (the group's backend is stopped during a backend fix and started again after), and integration runs again: `integrationRounds` (config, default 2) integration runs, so one fix round fewer. A failed fix child fails the group at once. A backend that does not come up counts as a failed round (`group_step` with `failed`).
5. **End** (`group_end`): pass drops both checkpoints and records where each repo ended (`heads`); failure parks each repo's work on `orchestrator/failed-group-<stamp>` and resets it to the checkpoint (a repo whose park fails keeps its group checkpoint, recorded as `kept` in `group_end` and `last-run.json`, and the run prints `orch group rollback NAME` to recover it); stop (`orch group stop NAME` writes a stop file) parks as `interrupted-group-<stamp>`. On a usage limit, `--on-limit wait` (default) carries on: a member run waits for the reset and resumes its own parked work (as `orch run` does; the group sums its `goal_end` costs over the attempts), and a coordinator call that exits 3 answers `{limit, resetAt}`, so the group emits `waiting`, sleeps until `limitWaitUntil` (a stop ends the wait) and asks again. A stop while a member run waits finds that run's work on its own `interrupted-<ms>` branch, not in place: `group-member park` renames it to `interrupted-group-<stamp>` (`childInterrupted`: started after the group's stamp and built on its checkpoint). With `--on-limit stop` a usage limit in any child or the coordinator parks both repos as interrupted and exits 3. Exit codes: 0 pass, 1 fail, 3 usage limit, 130 stopped.

Budget with `--max-cost` (`childShare`): the build gets 60% (split over the repos that build), the rest is kept for integration and fix rounds, each taking what is left divided by the child steps still possible. Every call's cost counts toward it. A share that rounds to $0.0000 fails the step as used up (`costArgs`).

`orch group rollback NAME` undoes the last passed run: `last-run.json` in the group dir holds each repo's start commit (`checkpoints`), the end commit (`heads`) and the `stamp`. Both repos are checked first (`group-member verify`), then each is reset to its start commit with everything after it, also the person's later commits, parked on `orchestrator/discarded-group-<stamp>` (the note says how many); `rolledBack` is recorded and `group_rollback` emitted. After a failed run with `kept` repos, or a run that never finished (no `ok` in `last-run.json`: killed hard), it instead resets each repo whose group checkpoint is still there (`group-member has`) to that checkpoint, parking the work the same way, and drops the checkpoint. It refuses a failed run that parked both repos (already reset), a run with no checkpoint left, an already rolled back one, and a run inside a group.

### Queue and loop

`.orchestrator/queue.json` holds `{id, goal, status: pending|running|done|failed, note?}` (`note` explains a wait, shown in the UI queue). On start, `loop` resets items left `running` by a crash or Stop to `pending`. It picks the first pending item, runs it, then re-reads the queue before writing the result, so goals added meanwhile are kept. SIGINT finishes the current goal and exits. `loop` refuses `--dry-run`, since a planned-only goal would stay pending forever.

parsing. Only fixed tool categories are emitted, at most 50 events per task (the last signals the cap); the reducer
keeps the most recent eight. Activity does not prove a requested tool succeeded. Old histories still replay without
the new start or activity events.

--verbose`: orch takes the final `result` line, and reads the subscription's usage from the CLI's

not documented by the CLI; if it changes or is missing (API-key logins), there are no `usage` events and the caps do nothing.

## UI (`orch-ui/`)

The UI works on several repos at once: one **tab per repo**, each with its own goal form, settings,
queue, run panel and log. Each repo has a **session** in the backend: its own `orch` process, log and
events. One run per repo at a time (agents share that repo's working tree); at most `maxParallel`
repos run at once (default 2, 1-16) and further starts wait for a free slot, oldest first. The repos on one
Claude account share its usage limit, so the limit is the main brake on parallel runs.

The backend keeps these limits per Claude account (a profile's id, `""` for the default folder; the **global**
state carries the default account at the top level and every account under `accounts`). A repo counts against
its profile's account (`accountKey`; a group's repos share one). A hold on one account never stops another's
starts: `startNext` passes over a held start and starts the next one whose account is free.

- **Usage-limit hold.** When a repo reports the usage limit (`usage_limit`, or `waiting` with `until`),
  new starts on that account wait until the latest reset time. Running goals are not stopped; each waits
  on its own (`--on-limit`). The UI shows a banner with **Try now**, which lifts the hold early
  (`/api/clear-limit`, every account, or one with `profile`).
- **Daily budget** (optional, USD, local day; **Daily $** for the default account, `dailyBudget` on a profile for
  its own). The backend adds up `cost` from the cost events of that account's repos (Agent M's chat counts
  on the default account); the totals are stored, so they survive a restart the same day. Each new
  run gets `--max-cost` capped to what is left (its own `--max-cost` if lower). When it is used up, new
  starts wait for the next day (or a higher budget), and a running loop is stopped at its next
  `queue_item`. Runs that start together each get the whole remainder, so the total can overshoot by
  up to what one run spends.
- **Usage caps** (optional, percent of the 5-hour and weekly windows; one setting for every account). The
  backend keeps each account's latest `usage` reading from its repos and passes the caps to every run as
  `--usage-cap 5h=N,week=M`. In orch,
  before each agent call a reading at or over a cap either pauses the goal in place until that window
  resets (`--on-limit wait`, event `waiting` with reason `usage_cap`) or ends it like a usage limit
  (`--on-limit stop`). The backend also holds new starts on an account while its reading is over a cap;
  **Try now** forgets the readings. A call already running can go past a cap.

A start that waits is `queued` with a `waitReason`: the usage limit, the budget, a usage cap, or a free slot.

### Backend (`server.ts`)

The one backend, for both modes. Node `http` server on `127.0.0.1:4317` (`PORT`; 0 picks a free port). Spawns `orch.ts` through tsx in each repo, or the bundled `orch.mjs` directly when `ORCH_PATH` names it. Opens the repos
remembered in `~/.yaaiorch/ui.json` plus `ORCH_REPO` / `ORCH_REPOS` (separated by the OS path delimiter);
`MAX_PARALLEL` sets the limit.

**Request guard** (`refuse()`): any web page in the user's browser can send requests to `127.0.0.1`, so
every request must have a local `Host` header (`localhost`, `127.0.0.1` or `[::1]`, any port; this
defeats DNS rebinding), a browser's `Origin` header, when sent, must be a local page, and every `/api/*`
call must carry the process's random 32-byte session token in `x-orch-token` (or `?token=` for the
event stream, since `EventSource` cannot set headers). The UI reads the token from `GET /api/token`,
which another site cannot read (no CORS, and `Origin` / `Sec-Fetch-Site: cross-site` are refused).
The token changes when the server restarts; `transport.ts` then fetches it again, retries once, and
reconnects the event stream. Vite's dev proxy (`localhost:5173`) passes the checks.

### Desktop shell (`src-tauri/src/main.rs`)

Tauri v2. The app does not reimplement the backend: it starts `server.mjs` (esbuild of `server.ts`, in
`src-tauri/resources/` next to `orch.mjs`; lookup: `SERVER_PATH` / `ORCH_PATH`, dev build output, bundled resource) with
the bundled Node.js, in app mode:

- `PORT=0` and `YAAIORCH_APP=1`: once listening, the server prints `@@READY@@ {"port":N,"token":"..."}` on its stdout,
  which only the app reads; `/api/token` is closed. The token never goes through the environment, which orch and the
  agents inherit.
- `YAAIORCH_APP_ORIGINS`: the webview's origins (`tauri://localhost`, `http(s)://tauri.localhost`, and Vite's in a dev
  build) pass the `Origin` check and get CORS headers; a preflight is answered before the token check.
- `YAAIORCH_UI_SETTINGS`: `<app config>/repos.json`, the file the app has always kept (same keys), so open repos,
  limits and today's spend carry over.
- `YAAIORCH_PARENT_PID`: the server checks every 2 s that the app is alive, and otherwise stops every run and exits.

The webview keeps loading the bundled UI (first paint before Node is up; `Splash.tsx` shows until the first `init`)
and calls `server_info`, which waits up to 30 s for the ready line and returns `{url, token}` or the server's last
output. A supervisor thread drains the server's output, restarts it when it dies (up to 5 times in a row; the UI asks
`server_info` again after a lost connection, since port and token change) and, on exit, kills its tree
(`taskkill /T /F`, or the process group). Native features stay in the webview through Tauri plugins: the folder
picker (dialog), reveal and editor links (opener), notifications and the updater.

### Remote access (`remote.ts`, `tunnel.ts`)

Off at every start (never remembered); **Remote** in the sidebar (`RemoteAccess.tsx`).

- **Addresses and devices.** A quick tunnel gets a new address every time it starts, and a device's cookie only goes to
  the address it paired at. So the server drops every device at start (`remote.forget()`) and whenever the tunnel's
  address changes (`addressChanged`, from the tunnel's `on` state), keeping only name, browser and role (`former` in
  `devices.json`, at most 20). `cleared` counts the dropped devices for the PC's note until one pairs again; a pairing
  request from a known name and browser carries `before`, and the PC can allow it with that role
  (`/api/remote/decide {role}`). A phone that gets no answer for 30 s shows why (`LOST_PC`).

- **Tunnel.** `Tunnel` runs `cloudflared tunnel --no-autoupdate --url http://127.0.0.1:<port>` (a quick tunnel, no
  account) and reads the `https://<name>.trycloudflare.com` address from its output. `cloudflared` is downloaded on
  first use from the pinned GitHub release (`CLOUDFLARED_VERSION`, one asset per platform) into `~/.yaaiorch/bin` and
  must match the pinned SHA-256 (GitHub's digest of that file); macOS archives are unpacked with `tar`. It is
  restarted with backoff if it exits (a new address each time; up to 5 times in a row). `CLOUDFLARED_BIN` overrides
  the executable (a `.mjs` runs with node; `test/fake-cloudflared/cloudflared.mjs`).
- **Which requests are remote.** `viaTunnel`: Cloudflare's `cf-connecting-ip` / `cf-ray` headers (a client cannot
  strip them) or the tunnel's host name. Such a request never meets the local guard (`refuse()`), so neither a
  forged `Host` nor the local token helps: it is refused unless remote access is on and its `Host` is the tunnel's.
  Writes must carry `Origin: https://<tunnel host>`. Responses get `X-Frame-Options: DENY`, `Referrer-Policy:
no-referrer` and `nosniff`.
- **Pairing.** The PC asks for a code (`POST /api/remote/pair-code`; 16 random bytes, single use, 5 minutes; a new one
  replaces the old) and shows `https://<tunnel>/pair#<code>` as a QR code (`Qr.tsx`). The fragment is never sent by
  the browser, and `Pair.tsx` removes it from the address bar. `POST /api/pair {code, name}` (rate-limited: 5 misses per
  address and 20 overall per 10 minutes) creates a request and returns `{id, poll}`; the PC sees it on every page
  (`PairRequests`) with the device's name and browser and answers `POST /api/remote/decide`. The phone polls
  `POST /api/pair/status {id, poll}`; once allowed, that answer (only to the holder of `poll`, only once) sets the
  device cookie `yaai_device=<id>.<key>` (32 random bytes; `HttpOnly; Secure; SameSite=Strict; Max-Age` 90 days,
  renewed on use). `devices.json` (next to the settings, mode 600) keeps only SHA-256 of each key.
- **Roles** (`remoteRefusal`). `view` (every new device): GETs only. `control`: also POSTs, except `PC_ONLY` (token,
  opening and closing repos, new projects, reveal, writing agent files, groups, browser-script approval, settings and
  limits, clear-limit), `/api/remote/*`, and `decide-command` with `always` or `prefix`. **Remove** deletes the device
  and ends its open polls. The UI learns its role from the `client` event: a view-only device gets the main area in a
  disabled `fieldset`; a remote one never shows the PC-only controls.
- **Events for devices.** Quick tunnels pass a streamed response's headers but hold back its body, so devices use long
  polling: every `send` event also goes into a ring (3000, numbered), and `GET /api/poll?since=N` answers with the
  events after N at once, or waits up to 25 s for the next. A first poll, or one too far behind, gets `client` and a
  fresh `init`. `sendLocal` events (pairing requests, devices) never enter the ring.
- **Desktop.** The app passes the built UI (`resources/dist`, a Tauri resource) as `YAAIORCH_DIST`, so the phone gets
  the same UI the window shows. Request bodies are capped at 2 MB for everyone.

## Concurrency and state files

- **Run lock** (`.orchestrator/run.lock`): `run`, `loop`, `learn` and `rollback` take it, so only one orch drives a
  repo. It records pid, host, command and start time; the holder touches it every 30 s and removes it on exit
  (only if it is still its own). A new process takes it over only if the holder's process is gone (same host)
  or the lock has not been touched for 2 minutes (a reused pid, or another machine); otherwise it stops with
  who holds it. `add`, `status` and the UI's reads do not take it.
- **Queue edits** (`updateQueue`): every read-modify-write of `queue.json` (`add`, the loop claiming and
  finishing goals) runs under a short `.orchestrator/queue.lock`, so goals added while a loop runs are never
  lost; a queue lock older than 10 s is from a process that died mid-edit. The browser server adds goals
  through `orch add` for the same reason.
- **Atomic writes**: `queue.json`, `last-run.json`, `brief.md` and `notes.md` are written to a temp file and
  renamed (retried briefly on Windows while a reader has the file open). A `queue.json` that is not valid is
  reported and left untouched, never overwritten.
- **Stop after this goal**: `orch stop-after` (or the UI's **Stop after this goal** while a queue runs)
  creates `.orchestrator/stop-after-goal`; the loop checks it before each goal and while waiting for a usage
  limit, removes it and exits with `loop_stop`. A request left from an earlier loop is cleared at start.

## Design decisions

- **Headless CLI per agent, not an SDK session.** One process per agent keeps isolation simple and reuses the user's Claude Code login, agents and skills. Cost: no streaming from inside an agent, and no shared context between agents (tasks must be self-contained).
- **Exclusive file ownership.** The architect assigns each file to one task. That is what makes parallel build safe in a single working tree.
- **Structured events on stdout.** One protocol serves the server and the CLI. Adding a UI never requires touching the loop.
- **Same UI, two transports.** `transport.ts` is the seam; the web build stays usable without Rust.
- **Node required at runtime.** The orchestrator is bundled as JS, not as a native binary.

## Testing

- Rust: `cargo test` in `src-tauri` spawns the real `orch.mjs` with a fake `claude` and asserts the event sequence, double-run refusal and clean exit. It is skipped unless `TEST_REPO`, `ORCH_PATH`, `CLAUDE_BIN` are set.
- Frontend: `npm run build` runs `tsc`. There are no unit tests yet.
