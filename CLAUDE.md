# YAAIORCH (Yet Another AI Orchestrator)

Display name: **YAAIORCH**. Desktop exe `yaaiorch.exe`, Tauri identifier `dev.alinion.yaaiorch`. Internal names stay short
and unchanged on purpose: `orch.ts`, `orch-ui/`, the `.orchestrator/` state dir and `orchestrator/*` git branches in target
repos, `ORCH_*` env vars and the `@@ORCH@@` event marker. Renaming those would break existing target repos and the protocol.

`orch.ts` is a CLI loop: an architect agent plans a goal, then F/E, B/E and other agents build in parallel,
then QA verifies. It repeats until QA passes or max rounds is reached. Built-in agents (`architect`, `fe`,
`be`, `qa`) live in `orch-agents.ts`; agents in `~/.claude/agents` and the target repo's `.claude/agents`
are discovered too and override built-ins of the same name. `orch-ui/` is a React UI that runs in the
browser (via `server.ts`) or as a Tauri v2 desktop app (`src-tauri`, which runs the same `server.ts`).

## Layout

- `orch.ts`: orchestrator CLI. Must sit next to `orch-ui/` (the UI looks for `../orch.ts`).
- `orch-browser.ts`: browser checks (find Chrome/Edge/Chromium/Brave, the dev server, CDP capture over Node's WebSocket, `orch browser login|install`), bundled into `orch.mjs`.
- `orch-awake.ts`: keeps the computer from sleeping while a long command runs (`--keep-awake`, config `keepAwake`): a per-OS helper (`awakeCommand`) tied to orch's PID, bundled into `orch.mjs`.
- `orch-ui/remote.ts`, `orch-ui/tunnel.ts`: remote access. `Remote` (pairing codes, requests the PC allows, device keys hashed in `devices.json` next to the settings, roles `view`/`control`, `remoteRefusal` + `PC_ONLY`; `forget` at every start and `addressChanged` per new tunnel address drop the devices, keeping name, browser and role for re-pairing; remote access is never persisted); `Tunnel` runs a Cloudflare quick tunnel (`cloudflared` downloaded to `~/.yaaiorch/bin`, pinned `CLOUDFLARED_VERSION` + SHA-256; `CLOUDFLARED_BIN` overrides, a `.mjs` runs with node: `test/fake-cloudflared/`).
- `claude-bin.ts`: finds the `claude` executable once (Windows: an .exe directly, an npm .cmd shim unwrapped to node + its script), shared by `orch.ts` and `evals/run.ts`.
- `orch-group.ts`, `orch-group-run.ts`: repo groups (config, coordinator prompts and parsing; the `orch group run` process), bundled into `orch.mjs`.
- `orch-agents.ts`: built-in agent prompts, bundled into `orch.mjs`. Written to `.orchestrator/builtin-agents.json` at run time and passed to `claude --agents`. Reply formats are appended to prompts by `orch.ts`, not stored here.
- `orch-events.ts`: the event payload types (`OrchEventData`, `OrchEvent`), `EVENT_TYPES` and `COST_EVENTS`, shared by orch, the browser server and the UI; no imports.
- `orch-ui/src`: React + TypeScript + SCSS. `transport.ts` talks HTTP/SSE to the server in both modes (desktop: address and token from the app's `server_info`; native folder picker and reveal); `Splash.tsx` shows until the first state arrives.
- `orch-ui/src/reduce.ts`: folds structured events into the run view.
- `orch-ui/server.ts`: the one backend. Spawns orch (orch.ts through tsx, or the bundled orch.mjs), forwards events over SSE. Bundled as `src-tauri/resources/server.mjs` (`npm run build:server`) for the desktop app.
- `orch-ui/src-tauri/src/main.rs`: desktop shell only. Starts `server.mjs` with the bundled Node.js (`node_bin`: `YAAIORCH_NODE`, else the `node` sidecar next to the app, else PATH) in app mode (`YAAIORCH_APP=1`, port 0, `YAAIORCH_APP_ORIGINS`, settings in the app's `repos.json`, `YAAIORCH_PARENT_PID`), reads its `@@READY@@ {port, token}` line, answers `server_info`, restarts a server that dies, kills its tree on exit. No orch logic here.
- `orch-ui/scripts/fetch-node.mjs`: downloads and SHA-256-checks the official Node.js for the build target into `src-tauri/binaries/node-<triple>` (Tauri `externalBin`; `universal-apple-darwin` via lipo). Run by `beforeDevCommand` / `beforeBuildCommand`; `VERSION` pins it.

## Event protocol

With `ORCH_EVENTS=1`, orch.ts prints one `@@ORCH@@ {json}` line per event: goal_start, queue_item, round_start,
architect_start, checkpoint, plan, checks_start, checks, visual_start, visual, task_start, task_activity, task_end, round_diff, round_end, stuck, critic, review, split_proposal, coverage, retry, blocked, queue_changed, question_wait, question_answered, command_wait, command_decided, resumed, intake, protected, secrets, ci, approval_wait, approval, goal_branch, pr, learn_start, learn_end, notes_tidy, share_start, share_end, loop_stop, unowned, usage_limit, goal_end, waiting, usage, history_error, group_start, group_plan, group_approval_wait, group_approval, group_step, group_child, group_fault, group_rollback, group_branch, group_end. Each event's payload is typed in `orch-events.ts` (`OrchEventData`, one
discriminated union `OrchEvent`): `emit` in `orch.ts` / `orch-group-run.ts` and the UI's `reduce.ts` use it, so a
renamed field fails the typecheck. Add a new event there first (and to `EVENT_TYPES`); a unit test checks this list
and the ARCHITECTURE.md table name every type; `server.ts` imports `COST_EVENTS`. The UI also folds a synthetic
`stopped` event (from `useOrch.ts`) when the process exits without `goal_end`.

## Notes

- Windows is the primary target. `claude` is spawned without a shell (`spawnClaude` / `claudeSync` in orch.ts, `resolveClaude` in `claude-bin.ts`); cmd.exe only as a fallback for a .cmd shim it cannot read. PATH is searched, never the current directory. Children use `windowsHide`.
- Server guard: `refuse()` in `server.ts` checks a local `Host` and `Origin` and a per-process token (`x-orch-token`, or `?token=` for SSE) on every `/api` call; the browser UI gets it from `/api/token` (`transport.ts`). In app mode the token goes only to the app (the ready line on stdout), `/api/token` is closed, and only `YAAIORCH_APP_ORIGINS` get CORS headers (preflight before the token check). Any new route is covered automatically; never add an `/api` route before the guard. Through the tunnel (`viaTunnel`: Cloudflare's `cf-*` headers or the tunnel's host) the local guard never applies: only `/api/pair`, `/api/pair/status` and static files without a device cookie, writes only from the tunnel's own origin, `remoteRefusal` for the device's role. A new route that writes to the PC (paths, files, scripts, limits) goes into `PC_ONLY`. Devices get events by long polling (`/api/poll`, the `send` ring), never `sendLocal` ones; request bodies are capped at 2 MB.
- Multi-repo UI: the server keeps one session per repo (process, log, events), tags every message with its `repo`, and runs at most `maxParallel` repos at once (start queue). One run per repo. Stop kills that repo's process tree (taskkill on Windows). Backend features go into `server.ts` only; `main.rs` stays a shell.
- Plugins: headless agents load the user's Claude Code plugins and hooks. `--plugins off` / `--disable-plugins` / `--no-hooks` (config `plugins`) write `enabledPlugins: {id: false}` and `disableAllHooks` into the agents' `--settings` files (not `--bare`, which drops the OAuth login). `orch plugins --json --details` lists them via `claude plugin list --json` and `claude plugin details`.
- Usage caps: agents run with `stream-json`; orch reads the CLI's `rate_limit_event` (5-hour and weekly `utilization`, undocumented) into `usage` events and, with `--usage-cap 5h=N,week=M` (config `usageCap`), pauses before an agent call (or stops, with `--on-limit stop`) while a reading is over a cap. The server passes its global caps to every run and holds new starts too.
- Global state (the server's `global` event): a usage limit in any repo holds new starts everywhere until the reset ("Try now" clears it); the optional daily budget sums `cost` from the cost events (`COST_EVENTS` in `server.ts`) and Agent M's chat, caps each run's `--max-cost` to what is left, holds starts and kills a loop at `queue_item` when used up. Persisted with the repos.
- `.orchestrator/` (queue.json, last-run.json, builtin-agents.json) lives in the target repo and is never committed by the orchestrator. State files go through `writeFileAtomic`; queue edits through `updateQueue` (queue.lock); `run`/`loop`/`learn`/`rollback` take `run.lock` (`acquireRunLock`). Never write queue.json directly, from orch or a backend (the browser server adds goals via `orch add`). `validate()` rejects plan paths outside the repo, in `.git`/`.orchestrator`, or through a link (`badPath`).
- Open in editor: `OpenIn.tsx` opens the repo through the editor's URL scheme (`editorLinks.ts`, unit-tested; the desktop capability allows only those `<scheme>://file/*` URLs). The file manager: `revealItemInDir` (desktop) or `/api/reveal` (browser server, explorer/open/xdg-open with the repo path as an argument).
- Notifications: `orch-ui/src/notifyText.ts` (pure, unit-tested) picks the events, `notify.ts` sends them (Tauri `tauri-plugin-notification`, capability `notification:default`, or the browser Notification API); called from `useOrch.ts` for live events only.
- Big briefs: `orch split` (`splitBrief` / `acceptSplit`, `--propose`, `--accept` from stdin, `--start`) and `orch new` share one splitter; the brief lives in `.orchestrator/spec.md` (read by every architect via `specForPrompt`), queue items from it carry `fromSpec`, and `coverageCheck` runs when the loop's queue is empty (two passes per brief, `.orchestrator/spec-state.json`). UI: `Brief.tsx`, the proposal comes from a `split_proposal` event without `queued` (`Session.proposal`). **+ New project** (`NewProject.tsx`) calls the server's `/api/new-project`: it creates `<parent>/<name>` (a plain name), open it as a repo and start `orch new .` there with the spec in a temp file.
- Safety: `protect` (default `.github/workflows/`, `protectedBy` in `validate` and before the commit, `revertPaths`), `scanSecrets` (added lines, new files, `.env`) and `largeFiles` (new or changed files over `maxFileSize` MB, default 5, `--max-file-size`); `commitAll` refuses both unless parking, and either fails the round. Never log a secret's value.
- PR CI: `watchPullRequest` (after `finishGoalBranch` in `runGoal`'s finally) waits on `gh pr checks`, runs fix goals (`runGoalInner` with a `title`) on the PR branch and pushes; fake `gh pr checks` follows `FAKE_GH_CHECKS`.
- Issues: `priorityOf` (labels → `priority`, `nextRunnable` picks the lowest), `commentIssue` on start / done / failed / blocked (`ISSUE_COMMENTS`). Never write "#N" for a queue goal in a comment.
- Intake: `orch intake` / `loop --intake` (`githubIssues` via gh, `backlogItems` from `- [ ]` lines), queue items keep `issue` / `backlog` so nothing is queued twice; a PR from an issue says `Closes #N`. Fake `gh issue list` reads `FAKE_GH_ISSUES`.
- Interrupted goals resume from their parked work: `lastParked` (set by `finishGit` / `finishGoalBranch`), queue item `resumeFrom`, `applyParked` after the checkpoint, and a note to the architect.
- Queue dependencies: items have `after` (ids), `brief`, `attempts`, `power`, `cost`, `seconds`, `resumeFrom`; status `blocked`. `nextRunnable` / `blockDependents` / `retryGoal` (`orch retry ID`); `--retries` (default 1) re-runs a failed goal a tier up, never after `BudgetExceeded`. With `--branch`, a brief's goals share `orch/brief-<id>` (`startGoalBranch(goal, id, brief)`), failed ones are parked, one PR per brief (`briefPullRequest`).
- Daily budget left goes to `loop` / `new --start` as `--max-cost-total` (`withBudget` in `server.ts`), else as `--max-cost`. Links out of the desktop app go through `tauri-plugin-opener` (`opener:default`).
- Progress: `orch-ui/src/progress.ts` (pure, unit-tested) from the queue; the server re-sends the queue on `queue_item`, `queue_changed`, `blocked`, `coverage`. The UI's queue **Budget $** and New project **Total $** pass `maxCostTotal` (`--max-cost-total`).
- Greenfield: `orch new` (`newProject`) creates the repo, seeds the brief and queues the architect's goals; checks are re-read every round (`refreshChecks`); config `setup` runs in `runSetup` before the checks when a manifest changed (hash in `.orchestrator/setup-state.json`), new untracked dirs go to `.git/info/exclude`. Agents never install.
- Agent M (`--commands`, config `commands: "ask"`, `commandTimeout`): implementers' `claude` gets a per-call `--mcp-config` (`.orchestrator/agentm-<pid>-<n>.json`, `permitConfig`) and `--permission-prompt-tool mcp__agentm__approve`. The MCP server is `orch permit` (`permitServer`, JSON-RPC over stdio, nothing else on stdout): shell tools write `.orchestrator/commands/<id>.json` and wait for `orch decide ID allow|deny|always` (`decideCommand`, claim file, run-lock check; `always` adds `Bash(<cmd>)` to config `allow`, refused by `alwaysBlocked` for `*`, parentheses or a secret; `command_wait` then carries `noAlways`; `prefix` (`orch decide ID prefix`) adds `Bash(<two words>:*)` when `prefixRule` offers one (event field `prefix`; never shells, interpreters, destructive or run-any-package commands), matched by `allowedBy` for single commands only; `orch allow [--json] [--remove RULE]` lists and removes them, server `/api/allow`, UI `AllowedCommands.tsx` in run settings), other tools are denied as before. The run's `scanCommands` emits `command_wait` / `command_decided`; a waiting command pauses `--agent-timeout`; when an agent call ends, its still-waiting commands are cancelled (`cancelCommands`). Server: `/api/decide-command`. UI: `AgentM.tsx` (page, `CommandCard`, nav count). Fake claude: `FAKE_COMMAND`.
- Agent M chat: `orch chat` (`chat`, JSON {question, session?, repos, running} on stdin, prints {answer, session, cost}) runs `claude -p --model haiku` in `~/.yaaiorch/agent-m` (`ORCH_CHAT_DIR`; `--resume` needs a fixed cwd) with Read/Grep/Glob only, `--strict-mcp-config` and `--add-dir` per repo. The prompt carries `machineStatus` (doctor, plugins, `claude mcp list`; cached 10 min in `context-cache.json`; `orch chat --warm` fills it when the page opens, and a question waits on its `context-cache.lock` rather than gathering twice) and `repoStatus` per repo (queue, last run, recent runs and failures, brief), redacted. Server: `/api/agent-m/ask` (cost through `addSpent`); UI `useAgentMChat` lives in `App` so the conversation survives page switches; answers render through `markdown.ts` (pure, unit-tested, no HTML). All agent text in the UI (plans, approvals, group goals and contract, reports, failures, questions) goes through `AgentText.tsx`: Markdown plus `structureText`, which shows a long single paragraph one sentence per line. Warm-up: `/api/agent-m/warm`. Fake claude answers prompts starting "You are Agent M".
- Plan approval (`--approve-plan`): `awaitDecision` writes `.orchestrator/plan-pending.json` and polls `plan-decision.json`, which only `orch approve` writes (the server calls it; an edited plan goes on stdin). A rejection re-plans with the human's reason.
- Branch per goal (`--branch`, `--pr`): `startGoalBranch` / `finishGoalBranch` / `openPullRequest`; the base branch never moves, the checkpoint is deleted at the end. The push is plain git (any host); `gh` runs only for a GitHub origin (`remoteWeb` / `forgeOf` on `remote.origin.url`), is resolved with `resolveCommand` (`GH_BIN`, fake in `test/fake-gh/`) and gets the PR body on stdin. Other hosts, or no `gh`: the `pr` event carries `link` (`pushLink` from the push output, else `newPullRequestUrl`). Tests fake a host with `bareOrigin(dir, url)` (`url.<bare>.insteadOf`). `orch new --remote URL` (`checkRemote`, `connectRemote`: origin plus a push of main; **Remote** in New project) and `orch doctor --pr` (from the UI's PR switch: `remoteFindings`).
- Git: a run refuses a dirty tree, creates `orchestrator/checkpoint-*`, and commits each round on the current branch. On pass the checkpoint is deleted, but only if everything got committed (a failed commit keeps it). Parking commits (`moveWorkAside`, side branches only) use `--no-verify` so hooks never block recovery; round commits respect hooks. On failure in `loop`, the work moves to `orchestrator/failed-*` and the branch is reset to the checkpoint. `orch rollback` (and the UI button) resets to the checkpoint and keeps the discarded work on `orchestrator/discarded-*`; `orch prune` deletes old `orchestrator/*` branches.
- Gate checks (config `gateChecks`, `loadGateChecks`, read once per run): orch runs them after the ordinary checks pass, never on the agents' allow-list (`gateOverlap` warns at start and in doctor), names only in prompts (`gateHint`, `GATE_HINT`); `checks` event `gate` / `gateSkipped`. The eval runner's gate cases keep their suites outside the repo (`evals/gate/<id>/`).
- Headless agents get no shell unless allowed: `claude -p` with `acceptEdits` refuses every Bash/PowerShell call that needs permission (Claude Code still runs commands it treats as read-only, such as `echo`, `ls` or `git status`, without asking; with `--commands` the rest go to Agent M). So orch.ts runs the repo's checks itself (`.orchestrator/config.json` `checks`, else package.json `typecheck`/`lint`/`test`/`build`) and a non-zero exit fails the round. Agents get an allow-list for those commands via `--settings`.
- Read-only roles (architect, verifiers) run with `--permission-mode default` and `readonly-settings.json` (edit tools denied). Deny rules alone are not enough: under `acceptEdits` an agent writes files with a shell redirect instead.
- Limits: `--agent-timeout` (30 min, kills the process tree), `--max-cost` per goal (each call reserves its share of what is left and gets it as `--max-budget-usd`; parallel build tasks split it equally; CLI reports `error_max_budget_usd`). Stuck rounds (no file changed, or same failures again) move up one power tier: only the failing tasks' agents when others completed (`agentPower`), else the whole round; two in a row stop the goal. Fix rounds give the architect `previousRound()` (plan, task statuses, diff stat); `.orchestrator/brief.md` is the architect's project brief (commit-stamped; checked again after 20+ changed files; `orch learn` writes it up front), reused across rounds, goals and all agents via `ctx.repoContext` (`--no-brief`); `.orchestrator/notes.md` collects lessons between goals (`appendNotes`, `--no-notes`). `--critic`: the built-in read-only `critic` agent reviews each plan once (event `critic`). Diff reviews next to QA (event `review`, skipped when a check or task failed): `--diff-critic` (critic, lens goal) and `--review` (built-in `reviewer`, or `--reviewers A,B`, lens bugs); a rejection fails the round. The critic, `reviewer` and named reviewers are excluded from the architect's roster. `tidyNotes` merges notes.md past 5000 characters (event `notes_tidy`); `orch share` commits a CLAUDE.md section (between `yaaiorch:learned` markers) on an `orchestrator/claude-md-*` branch with git plumbing, never touching the working tree. The server counts the cost of plan, task_end, review, learn_end, notes_tidy, share_end, split_proposal, coverage, group_plan and group_fault, plus Agent M's chat (`addSpent`).
- Transient API errors (`TRANSIENT_RE`) are retried once in `run()`; files changed outside every task's list are reported (`unowned`; `--strict-files` fails the round); `--max-cost-total` caps a whole `loop`. Export new pure helpers at the bottom of orch.ts for unit tests.
- Session resume (`--no-resume`, config `resume`): a fix round's implementer task continues the session (`--resume <id> --fork-session`) of the same agent's task from the round before that shares a file with it (`pickSession`); the prompt is then the task alone. Not after a stuck round (fresh look), never for QA or the architect; a failed resume starts cold once; a phantom retry continues its own session with a nudge. `task_start` carries `resumed: <round>`.
- Fast path (default; `--no-fast`, config `fast: false`): round 1 is a single built-in `dev` agent (strong model, no file list) judged by the checks (QA only without checks); failure falls back to the full loop. `--approve-plan`, `--critic` and `--dry-run` turn the default off (an explicit `--fast` wins). The server passes `--fast` / `--no-fast` from the UI's checkbox. The eval runner passes `--no-fast` for a plain tier; `+fast` is the direct attempt. Scenario tests run the full loop unless they pass `--fast`, `--no-fast` or `default` first (`fullLoop` in `scenarios.test.mjs`). Results: `docs/evals/2026-11-18.md`.
- `orch doctor --json` is the first-run check both UIs show as a banner.
- Keep awake: `wantsAwake` (run, loop, new --start, group run; not member runs) starts `keepAwake()` in `main`; the server's global switch (`keepAwake`, default on, `/api/settings`) adds `--keep-awake` via `withAwake`. Only idle sleep is blocked.
- Usage limit ("You've hit your … limit · resets …"): ends the goal as `UsageLimit` (never a task failure or stuck round). `--on-limit wait` (default; config `onLimit`): the work goes to `orchestrator/interrupted-*`, orch waits for the reset and retries (`run` and `loop`). `--on-limit stop`: the goal stays pending and orch exits 3. The eval runner always passes `--on-limit stop` and never records such runs: it stops (or waits with `--wait-on-limit`), and `--resume <stamp>` finishes later.
- Models: `modelFor()` resolves per-agent override > per-role override (`--model`, then config `models`) > power tier. Roles: architect, impl, heavy, qa, dev. On stuck escalation alias overrides step up (haiku → sonnet → opus); full IDs stay. `round_start` carries the effective `models`. The UI's `Settings.tsx` mirrors the tier table for placeholders; keep it in sync with `POWER`.
- Agent swaps: config `"swap"` maps a built-in role (`architect`, `fe`, `be`, `qa`, `dev`, `critic`, `reviewer`, `coordinator`) to a custom discovered agent. Plans and events keep the role name; `runOnce` uses `Entry.runAs` for `--agent` and omits `--agents`. Read-only mode and models remain role-based. `orch agents --swap/--unswap` edits this atomically; the Agents UI uses it through the server.
- Skills and agents per repo: config `skills.disable` / `agents.disable` (`orch agents --disable-skill|--enable-skill|--disable-agent|--enable-agent NAME`, `setDisabled`; refuses built-ins and swap targets). `configuredRoster` drops disabled custom agents (a swap target stays), `configuredSkills` drops disabled skills from the architect's list, and `writeAgentSettings` writes `skillOverrides: {NAME: "off"}` and a `Skill(NAME)` deny rule into both settings files. `agents --json` carries `disabled`. Server: `/api/agents/toggle`; UI switches in `Agents.tsx`.
- Browser checks (config `serve` {url, command, timeout}; `--no-visual`): verify tasks may carry `visual` (pages, selector, click/wait actions, widths, themes; `validateTargets`, at most 5 per plan). After clean checks orch starts the dev server (`DEV_SERVER`, killed on exit), runs `captureVisual` on the repo's own profile (`profileDir`) and passes `visualReport` to QA. Problems (does not render) fail the round; observations (console, page errors, requests, overflow, CLS) are for QA. Only localhost (`isLocalUrl`); no browser is bundled. Scenarios in `test/scenarios.test.mjs` use a real browser and `test/fixtures/visual-app.mjs`, skipped when none is installed.
- Repo groups (`orch group add|list|remove|run|stop|rollback`, config `~/.yaaiorch/groups/<name>.json`, `YAAIORCH_HOME` moves it): one goal across exactly one backend and one frontend repo. `orch group run` (`runGroup`) holds the group lock and both repos' run locks (children inherit `ORCH_GROUP_LOCK`), runs a coordinator (hidden `orch group-member coordinate` in the backend repo) for the contract (`.orchestrator/contract.md` in both repos) and a goal per repo, builds both in parallel as `orch run` children (`--group-context`, `--read-dir` of the other repo with writes denied in settings, `--strict-files`, `--no-commands`, the group's `--on-limit`; the repo's own branch, pr, approvePlan, worktrees and ask are ignored), then starts the backend (`DevServer`, an answering server is reused) and runs a `--no-fast` frontend child against it with `--probe <backend>` (every agent call gets `orch probe`, an MCP server whose `request` tool reaches that backend's origin only, `probeServer` / `probeTarget`, allowed with `--allowedTools mcp__probe__request`; `integrationGoal` requires live checks, an unchecked case is a failure, and carries the frontend's build goal, whose names and return shapes it must keep); the frontend `env` (`{backend}`) goes to all the frontend's children. A failed integration asks the coordinator for a fault call (fix goals only for the side(s) at fault, contract may be revised), up to `integrationRounds` (2); a failed fix child fails the group. Failure parks both repos on `orchestrator/failed-group-*` and resets them (a member run the group killed has the git locks written since its start removed first, `clearGitLocks`), stop uses `interrupted-group-*`, a usage limit waits by default (`--on-limit`, passed to the members, which wait and resume their own parked work; a coordinator call that exits 3 answers `{limit, resetAt}` and the group waits (`waitOutLimit`, `limitWaitUntil`) and asks again), with `--on-limit stop` it parks as interrupted and exits 3. `orch approve --group NAME` answers `--approve-plan`; `orch group rollback NAME` resets both repos to their start commits (later commits parked too). `--branch` / `--pr` (`GroupOpts.branch`/`pr`; UI **Lands as**): `branchAll` after the checkpoints (`group-member branch`, `groupBranchName`, `--pr` refuses without origin), `unbranch` back to the base after a park or a pass (an empty group branch is deleted), `publishBranches` on pass (`group-member publish`, `pushAndRequest`; backend first, then `group-member pr-body` links it to the frontend's; `groupPrBody`), event `group_branch`, last-run `branches` (rollback refuses those). Fake gh: `FAKE_GH_PR_BY_DIR`, `pr edit`. Every repo-level git step is a hidden `orch group-member` call. The server counts `group_plan`/`group_fault` cost and unwraps `group_child` to an idle member session (kept wrapped when that repo has its own run). UI: a group is a session keyed by its run dir (`dir` from `orch group list --json`, `syncGroups`, never in the remembered repos); its `run` is `orch group run`, `approve` adds `--group`, `rollback` is `orch group rollback`, Stop calls `orch group stop` (tree kill only if that fails); while it runs or waits, member sessions report `inGroup` and refuse starts, and a group start is refused while a member runs; members open as tabs on start. `/api/group-save` (`orch group add`, which keeps an existing group's `contract` and `integrationRounds`), `/api/group-remove`. Page: `GroupView.tsx` (`GroupDialog` for the form). `--max-cost` split: see `childShare`. Fake claude: `FAKE_PROMPTS`, `FAKE_GROUP_FAULT`, `FAKE_GROUP_REVISE`, `FAKE_QA_FAIL_INTEGRATION`, `FAKE_HANG_REPO`.
- Testing without spending tokens: `CLAUDE_BIN=test/fake-claude/claude` (`claude.cmd` on Windows); switches are documented at the top of `fake-claude.mjs`. Spawn `claude` only through `spawnClaude` / `claudeSync` (or `resolveClaude`), never with `shell: true`.

## Evals (`evals/`, see its README)

- `node evals/run.ts --reference`: checks every case's hidden tests fail on the fixture and pass with the reference. Run after editing a case.
- `node evals/run.ts --cases <ids> --power economy,heavy`: real runs (costs money), graded by hidden tests the agents never see. Results in `evals/results/` (git-ignored).
- Use it to judge prompt, agent or tier changes: compare hidden pass rate, false passes and cost before and after, with `--repeat 3` or more.
- Group cases (`group` in `cases.json`, fixtures `group-shop-api` + `group-shop-web`): `orch group run` in the run dir with its own `YAAIORCH_HOME`; hidden tests and references per role (`hidden/<id>/backend|frontend`); the frontend grade gets `EVAL_BACKEND` and drives the web client against the run's backend (`evals/lib/backend.mjs`). Tier plus `+fast` only, no single control.
- Config suffixes: `economy+fast`, `+nomem` (no brief or notes), `+critic`, `+noresume`, `+diffcritic`, `+review`, combinable. Series cases (`goals: [...]` in `cases.json`) run each goal in turn on one repo and grade at the end; they measure the brief and notes (`--power economy,economy+nomem`).
